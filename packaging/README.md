# Packaging

Five distributable formats, one entry point. Every build runs inside its own
container, so the host only needs Docker and nothing leaks in from the
developer's machine — the Windows bundle included, which is cross-built on
Linux like the rest.

```bash
make appimage        # or: ./packaging/build.sh appimage   (x86_64 hosts only)
make deb             # or: ./packaging/build.sh deb
make rpm             # or: ./packaging/build.sh rpm
make flatpak         # or: ./packaging/build.sh flatpak
make windows         # or: ./packaging/build.sh windows    (needs `make vendor-retroarch`)
make packages        # all five, then `make checksums` over the result
make packages-clean  # wipe dist/ artifacts
make aur-git         # the AUR's openemux-git recipe; see "The AUR packages" below
make aur-release TAG=v1.24.0           # the three release AUR recipes, built and swap-tested
make aur-publish TAG=v1.24.0 DRY_RUN=1 # ...and the diff they would push to the AUR
```

Artifacts land in `dist/`. `make packages` finishes with `checksums`, which
writes a single `dist/SHA256SUMS` over everything in there — build an artifact
after it and it ships unverifiable, which is why `windows` comes before
`checksums` in the target's prerequisites.

## Layout

| Path | Responsibility |
| --- | --- |
| `build.sh` | Host-side entry point: builds the image, runs the target's build script in it |
| `docker/<target>.Dockerfile` | The build toolchain for one target |
| `<target>/build.sh` | What runs **inside** the container: build + install-test |
| `common/` | The install layout, the launcher, the desktop entry and the AppStream metainfo — shared by every format |
| `appimage/AppImageBuilder.yml` | The bundle recipe |
| `appimage/openemux-launcher.c` | The bundle's entry point — a static ELF, because `app_info.exec` cannot be a script |
| `appimage/openemux-run.sh` | What that ELF hands over to: the bundle's runtime env, then Python |
| `appimage/requirements.hashed.txt` | The bundle's Python deps, hash-pinned (generated by `appimage/hash_lock.py`) |
| `rpm/openemux.spec` | RPM metadata; unpacks a source tarball and installs via `common/stage_tree.sh` |
| `arch/PKGBUILD` | Arch recipe; unpacks the same source tarball and installs via `common/stage_tree.sh` |
| `aur/openemux-git/PKGBUILD` | The AUR's `openemux-git`: built from a git clone, same install layout, the distribution's RetroArch |
| `aur/build.sh` | Builds that recipe from this checkout, install-tests it and writes the files to publish |
| `aur/openemux/PKGBUILD`, `aur/openemux-bin/PKGBUILD`, `aur/openemux-appimage/PKGBUILD` | The AUR's release packages: templates for `aur/release.py` to fill in for a tag |
| `aur/release.py` | Writes the three release recipes for a tag: version, `pkgrel`, checksums |
| `aur/release.sh` | Builds, namcap-checks, install- and swap-tests them, then diffs or pushes them to the AUR |
| `deb/changelog_from_spec.py` | Renders the Debian changelog from the spec's `%changelog` |
| `flatpak/io.github.guilhermefeitosa66.OpenEmux.yaml` | The Flatpak manifest, with the `finish-args` rationale in its own comments |
| `flatpak/python3-*.yaml` | The Python modules the runtime does not carry (PyYAML, python-xlib, cryptography, zeroconf) |
| `windows/stage.py` | Assembles the portable bundle from the MSYS2 packages in `packages.lock` |
| `windows/openemux.nsi` | The NSIS script that turns the staged bundle into the installer `.exe` |
| `testenv/` | The distrobox matrix the built artifacts get install-tested in |

Building a package is only half of it. `testenv/` installs and launches the
finished artifacts on Ubuntu, Debian and Fedora, under X11 and Wayland --
`make ubuntu-x11`, `make testenv-matrix`. See
[`testenv/README.md`](testenv/README.md).

`common/` holds `stage_tree.sh` (the `/opt/openemux` install layout),
`copy_tree.sh` and `assert_sources_only.sh` (staging sources without the
working tree's build state, and proving it),
`openemux-launcher.sh` (the `/usr/bin/openemux` launcher), `openemux.desktop`
(the single desktop entry every format installs) and
`io.github.guilhermefeitosa66.OpenEmux.metainfo.xml` (the AppStream data every
format installs to `/usr/share/metainfo/`).

## The AUR packages

Four packages on the AUR. `openemux` is the plain name; the other three
`provides`/`conflicts` `openemux`, so pacman swaps any one for any other:

| Package | What it installs | Pick it when |
| --- | --- | --- |
| `openemux` | The stable release, built from the tag's source archive; the distribution's RetroArch | You want the release and the Arch way: system libraries, system emulator |
| `openemux-bin` | The release's own Arch package (`openemux-<v>-1-x86_64.pkg.tar.zst`), RetroArch bundled | You want the release without a build, exactly as the GitHub release ships it |
| `openemux-appimage` | The release AppImage under `/opt/openemux-appimage`, with the desktop entry and icon | You want the self-contained build, its own GTK stack included |
| `openemux-git` | Whatever is on `develop`, built from a clone; the distribution's RetroArch | You want the newest code and can live with it breaking |

### The release packages (`openemux`, `-bin`, `-appimage`)

Their recipes are templates: `pkgver=0.0.0`, `pkgrel=1` and
`sha256sums=('SKIP')`. `aur/release.py <tag> --out <dir>` fills them in for a
published release: the version from the tag, and the checksums of the files
they download -- the Arch package and the AppImage from the release's own
`SHA256SUMS`, and the tag archive (which no `SHA256SUMS` covers) hashed on
download. A release missing a file a recipe needs is an error, not a recipe.
Every download comes from this repository's GitHub release; the AppImage
recipe reads its desktop entry, icon, metainfo and licence out of the
AppImage itself.

`make aur-release TAG=vX.Y.Z` runs that in the Arch image, writes `.SRCINFO`,
builds each recipe as a user's makepkg would, runs namcap, installs
`openemux`, swaps it for `openemux-bin`, then `openemux-appimage`, then back,
and removes it. The files for the AUR land in `build/aur/release/<package>/`.
`PKGREL=2` regenerates a recipe fix for the same release.

**Publishing** is the `AUR` workflow (`.github/workflows/aur.yml`),
dispatched by the release process once the GitHub release exists:

```bash
gh workflow run aur.yml -f tag=vX.Y.Z -f dry_run=false
```

It runs `make aur-publish`, which does the whole check above, then commits
`PKGBUILD` and `.SRCINFO` to each AUR repository and pushes. It needs the AUR
account's SSH key in the repository secret `AUR_SSH_PRIVATE_KEY`; without it, a
publish fails before building anything and says so. A dry run (`dry_run=true`,
the default, or `make aur-publish TAG=vX.Y.Z DRY_RUN=1` locally) needs no
secret: it clones each AUR repository anonymously and prints the diff it would
push. The AUR's host key is pinned in `aur/release.sh`.

### `openemux-git`

`aur/openemux-git/PKGBUILD` is the recipe for the AUR, so Arch users can
install and update OpenEmux with `yay -S openemux-git` (or any AUR helper)
instead of downloading a release (issue #986). It builds whatever is on
`develop` at the time -- the `_branch` variable says so -- and differs from
`arch/PKGBUILD` in three ways:

- **Source:** a git clone, not a tarball packed from the working tree. The
  version is computed by `pkgver()`: `<__version__>.r<commit count>.g<sha>`,
  so `src/openemux/__init__.py` stays the one place it is written.
- **RetroArch:** the distribution's (`depends=('retroarch')`). A clone carries
  no vendored emulator, and downloading 171 MiB from the buildbot inside a
  build is not something an AUR recipe should do. Nothing is compiled or
  vendored, so it is `arch=('any')`.
- **Name:** `provides`/`conflicts` `openemux`, so it replaces a release package
  and the other way round.

`make aur-git` builds it in the Arch image from a bare clone of this
checkout's **HEAD** (commit first: uncommitted changes are not in it), installs
it with pacman, checks it and removes it. It then writes the two files the AUR
repository holds to `build/aur/openemux-git/`: the tracked `PKGBUILD` with the
version just built, and its `.SRCINFO`. Nothing goes to `dist/` -- it is not a
release artifact, and `make packages` does not build it.

Publishing, which needs an AUR account with an SSH key registered on it:

```bash
make aur-git
git clone ssh://aur@aur.archlinux.org/openemux-git.git /tmp/aur-openemux-git   # empty the first time
cp build/aur/openemux-git/PKGBUILD build/aur/openemux-git/.SRCINFO /tmp/aur-openemux-git/
cd /tmp/aur-openemux-git && git add PKGBUILD .SRCINFO && git commit -m "Update to <pkgver>" && git push
```

A `-git` package does not need a push for every commit -- AUR helpers rebuild
from the branch on their own (`yay -Syu --devel`). Push again when the recipe
changes: a new dependency, a change to the install layout. Keep its `depends`
in step with `arch/PKGBUILD`; `tests/test_aur_package.py` fails when they drift
(and `tests/test_aur_release.py` for the release recipes).

## Things that are easy to get wrong

**Interpreter selection (native packages).** The launcher must not use `python3`
from `PATH`. A version manager (pyenv, conda, asdf) puts a shim first, and those
interpreters have no PyGObject — a correctly installed app then dies with
`ModuleNotFoundError: No module named 'gi'`. The launcher walks candidates and
takes the first that can `import gi`. Both `deb/build.sh` and `rpm/build.sh`
regression-test this with a fake `python3` earlier in `PATH`.

**gdk-pixbuf loaders (AppImage).** The cache written while bundling records the
*builder's* absolute loader directory. Shipped as-is, every loader in it is
unreachable on the user's machine — no SVG, no WebP. `appimage/build.sh`
regenerates the cache from the bundled loaders and strips the build-time path so
entries are bare filenames, which `GDK_PIXBUF_MODULEDIR` resolves at runtime.
The build fails if the SVG loader is missing from the result.

**Runtime environment (AppImage).** appimage-builder generates its own `AppRun`
and overwrites anything shipped at `AppDir/AppRun`, and it refuses to deploy
unless `app_info.exec` is a real ELF — so neither of those can carry the setup.
The recipe points `app_info.exec` at `appimage/openemux-launcher.c`, a static
binary whose only job is to resolve `$APPDIR` and hand over to
`appimage/openemux-run.sh`, which sets the bundle's environment with the
recipe's `runtime.env` as a second layer. `GI_TYPELIB_PATH` matters most:
without it the `Rsvg` import fails and the cartridge frames silently degrade to
plain covers.

**Versions.** `src/openemux/__init__.py` is the single source of truth. The
`.deb`, `.rpm` and Flatpak read it at build time; the AppImage recipe carries
its own copy, and it is the only one that can drift — so `appimage/build.sh`
refuses to build when the two disagree, and
`tests/test_reproducible_builds.py` checks all four bump sites against it on
`develop`.

**The Flatpak sandbox confines almost nothing, on purpose.** Two of its
`finish-args` are the widest Flatpak has:

- `--talk-name=org.freedesktop.Flatpak` allows `flatpak-spawn --host` with
  arbitrary commands — unrestricted code execution outside the sandbox. It is
  used in exactly one place, `core/retroarch_launcher.py`'s `_launch_prefix()`,
  to run `flatpak run org.libretro.RetroArch`. OpenEmux is a front-end for an
  emulator that lives in its *own* Flatpak, and there is no portal for "start
  that other app on a ROM".
- `--filesystem=home` is load-bearing three times over: `~/.openemux` holds
  config/playlists/input/shaders/BIOS, the ROM library defaults to
  `~/games/roms` and can be anywhere, and RetroArch runs on the host with
  absolute paths — the ROM and the `--appendconfig` override — that have to mean
  the same thing on both sides.

The prerequisite for narrowing it is done: every file chooser now goes through
the XDG portal via `Gtk.FileDialog`, and no `Gtk.FileChooserDialog` — the
in-process widget, which could only ever reach what the sandbox already saw —
is left in the app (issue #235). The three reasons above still need settling
before the grant can become a portal-granted ROM directory. Until then the
rationale is written down in the manifest, where Flathub's reviewer will look
for it, and `tests/test_flatpak_sandbox.py` pins the permission set so a new one
is a deliberate edit rather than a line that slips through — it also fails if a
`Gtk.FileChooserDialog` comes back, since that would undo the prerequisite.

**The Flatpak sees every device node, for the controllers.** The gamepad
reader on Linux is evdev: it lists pads from `/proc/bus/input/devices` and
reads `/dev/input/event*`. With only `--device=dri` there is no `/dev/input` in
the sandbox, so no pad was ever seen there while every other format saw it
(issue 1001). `--device=all` binds the host's `/dev`, which also makes hotplug
work. The narrower `--device=input` needs **Flatpak 1.15.6**, and the floor
(Ubuntu 24.04, Linux Mint 22) ships 1.14.6, which rejects it as an unknown
device type; once the floor moves past 1.15.6, `--device=dri` plus
`--device=input` is the pair to switch to. `tests/test_flatpak_sandbox.py`
fails if the grant is dropped, and the test containers check it
(`make flatpak-devices` in `testenv/`). Remapping inside a Flatpak that had the
access removed (Flatseal, `flatpak override`) says so instead of reporting no
controller.

**TryExec belongs to the native packages only.** The shared
`common/openemux.desktop` carries none. `TryExec` is resolved against the user's
`PATH`, and AppImage integrators (appimaged, AppImageLauncher, GearLever)
rewrite `Exec` to the bundle path and leave `TryExec` alone — so an entry naming
`openemux` was silently hidden from the menu after integration.
`stage_tree.sh` adds an absolute `TryExec=/usr/bin/openemux` for the `.deb` and
`.rpm`, which are the builds that install that binary; the AppImage build fails
if the bundled entry has one at all.

**No `MimeType`, so no `shared-mime-info`.** The entry has no `MimeType=` and no
`%f`/`%U` — the app cannot open a ROM handed to it by a file manager — so the
hard dependency both native packages declared indexed nothing. GTK needs the
shared MIME database at runtime and already depends on it on both
distributions, so dropping the explicit declaration changes nothing for a user.
The AppImage still bundles it: `XDG_DATA_DIRS` leads into the AppDir, so GTK
looks for the database there. Declare it again on the day OpenEmux can open a
ROM from the file manager, together with the `MimeType=` line and `%U`.

**What ships is licensed.** About a third of every package is third-party: the
console icons are OpenEmu's (BSD-3-clause), the symbolic icons are Adwaita's
(LGPL-3 / CC-BY-SA-3.0) and the vendored RetroArch is GPL-3+. Every
format installs `common/copyright` — a DEP-5 file naming each — rather than a
copy of the MIT `LICENSE`, which claimed MIT over all of it. The notices ship
beside the artwork too (`ui/assets/icons/ATTRIBUTION.md`,
`ui/assets/icons/symbolic/LICENSE`), which is what OpenEmu's terms require of a
binary distribution, and `tests/test_icon_assets.py` fails when a vendored
directory has no entry.

**Reproducibility.** Every Docker base is pinned by digest and
`packaging/build.sh` builds with `--pull`, so a base-image change is a commit
somebody reviewed rather than a silent difference between two builds of the
same commit. Re-pin deliberately — `docker manifest inspect ubuntu:24.04`
prints the current digest. The AppImage's Python dependencies are installed
with `--require-hashes` from `appimage/requirements.hashed.txt`, generated from
`requirements.lock` by `appimage/hash_lock.py`; its apt sources and their
signing key are fetched over https, because everything they serve ends up
inside the signed release artifact.

**Container privileges.** Two builds mount a filesystem, and each gets only
what it needs — not `--privileged`, which is every capability, every device and
no seccomp, in a container that bind-mounts the repository and carries
`SCREENSCRAPER_DEVPASSWORD`.

| Build | Why | Flags |
| --- | --- | --- |
| AppImage | appimage-builder mounts squashfs | `--cap-add SYS_ADMIN --device /dev/fuse --security-opt apparmor:unconfined` |
| Flatpak | the above, plus bubblewrap bringing up loopback in a network namespace and calling `pivot_root` | the above plus `--cap-add NET_ADMIN --security-opt seccomp=unconfined` |

Both sets were established by probing the actual failures (`bwrap: loopback:
Failed RTM_NEWADDR`, `bwrap: pivot_root: Operation not permitted`), so removing
any one of them breaks a build rather than passing quietly.

**Staging is sources only.** Every format copies through
`common/copy_tree.sh` and checks the result with `common/assert_sources_only.sh`.
A plain `cp -r src` shipped whatever the maintainer's tree happened to hold:
the released `.deb` and `.rpm` both carried `opt/openemux/src/opemux.egg-info/`,
a directory named after a project name that no longer exists — its
`top_level.txt` registers a phantom distribution on
`PYTHONPATH=/opt/openemux/src`, and its `SOURCES.txt` publishes the development
tree's file inventory. The same list also keeps the 193 MiB Windows RetroArch
out of a Linux package built after `make vendor-retroarch`.

**AppStream metainfo.** Every format installs
`common/io.github.guilhermefeitosa66.OpenEmux.metainfo.xml` to
`/usr/share/metainfo/`; without it GNOME Software and KDE Discover know the app
only as a bare desktop entry — no summary, no screenshots, no release notes and
no update notification — and both rpmlint and lintian flag it. The `.deb`,
`.rpm` and Flatpak builds run `appstreamcli validate --no-net` over the file
they install, and `tests/test_appstream_metainfo.py` covers what a validator
cannot: that every shipped version is in the release history, and that the
screenshot URLs are pinned to a commit rather than to `main`. They are
re-indexed by the software centre long after the install, so a screenshot
refresh that renames a file under `docs/assets/` would blank them for everyone.

**The RPM must stand on its own.** `rpm/build.sh` packs a source tarball,
resolves `Version:` into the copy of the spec it hands to `rpmbuild`, and builds
with `-ba` — so the `.src.rpm` is self-contained and `rpmbuild --rebuild`,
`mock` and COPR need no OpenEmux checkout. The build proves it on every run by
rebuilding its own SRPM in a different `_topdir`, and runs rpmlint over both
artifacts, failing on the findings that block Fedora review. The spec was
previously driven with `--define "repo_root /work"` and had no `Source0`, so it
could only ever be built from this project's own Docker bind mount.

**The ScreenScraper credential.** `embed_screenscraper_credentials.py` rewrites
`_EMBEDDED_BLOB` in `core/embedded_credentials.py`, and every target must run it
against **its own staging copy** — `$DESTDIR` for the `.deb`/`.rpm`, `AppDir`
for the AppImage, the staged bundle for Windows, a `mktemp -d` tree for the
Flatpak. Never the working tree: the tracked file restored by a trap is one
`docker kill` away from leaving the project's credential in a committable file.
`build.sh` refuses to start when the tracked file already carries a blob, and
`tests/test_packaging_credentials.py` checks that no injection site targets it.

The Flatpak needs the extra staging step because its source is `type: dir`,
`path: ../..` — the *whole* directory beside the manifest, `.env` and `dist/`
included. `flatpak/build.sh` copies the build inputs into a staging tree and
builds the manifest from there; the manifest's own `skip:` list covers the two
paths that build the working tree directly (a developer running
`org.flatpak.Builder` by hand, and the `openemux-flatpak` publish workflow).
